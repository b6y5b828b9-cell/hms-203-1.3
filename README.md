# Run and deploy your AI Studio app

This contains everything you need to run your app locally.

View your app in AI Studio: https://ai.studio/apps/397c5678-6561-4bdf-a8f1-1401df1bfb2d

## Run Locally

**Prerequisites:**  Node.js


1. Install dependencies:
   `npm install`
2. Set the `GEMINI_API_KEY` in [.env.local](.env.local) to your Gemini API key
3. Run the app:
   `npm run dev`

## Shared clinic data setup

The application currently uses browser-local demo data. Do not enter real patient information or configure production sync until the clinic has an approved Supabase project, an appropriate healthcare privacy agreement, configured Auth users, and reviewed row-level security policies.

1. Apply all SQL migrations in `supabase/migrations/` in order to the approved Supabase project.
2. Create clinic memberships for authenticated users with the least-privilege role they need. Insurance status changes require the `medical-coder` membership role; nursing vitals and progress notes require the `nurse` role; lab, radiology, pharmacy, and billing users need their corresponding role.
3. Set `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, and the clinic UUID as `VITE_HMS_CLINIC_ID`.

The Supabase client is optional and remains disabled when these values are absent. Shared token synchronization also requires an authenticated Supabase session; the demo login does not create one. Do not upload mock or local browser records as part of setup. Production sync still requires authenticated app-session wiring and an explicit, audited data-import/cutover process. The token authorization contract is in [docs/visit-token.schema.json](./docs/visit-token.schema.json).

The insurance response handler updates linked token line items only for the `medical-coder` role. The repository does not include an eClaimLink/DHPO transport adapter or credentials; connect the payer API to the handler rather than treating manual status entry as an external response.

The outpatient nurse queue is filtered by department and doctor, shows Waiting, In Triage, In Consultation, and Ready for Treatment badges, and excludes closed visits for nurse users. For nurse accounts, `Nurse Triage Station` is grouped in its own Outpatient Nursing sidebar section. Opening a token shows a collapsible patient information card followed by Nurse Clinical Review, Doctor Services & Insurance Status (read-only), Outpatient Treatment Execution, Discharge & Instructions, Medical Reports, and Insurance & ID Documents tabs. Call-in uses `POST /rest/v1/rpc/advance_outpatient_nurse_token` with `{ "p_clinic_id": "<uuid>", "p_token_id": "<token-id>", "p_next_status": "In Triage" }`; the same RPC can advance eligible tokens to `Ready for Treatment`. Triage submission uses `POST /rest/v1/rpc/save_outpatient_nurse_triage` with `{ "p_clinic_id": "<uuid>", "p_token_id": "<token-id>", "p_vitals": { "bpSystolic": 142, "bpDiastolic": 95, "heartRate": 78, "temperature": 98.6, "respiratoryRate": 16, "heightCm": 170, "weightKg": 72.2, "spO2": 98, "painScale": 0, "triageLevel": "Level 3 - Urgent", "chiefComplaint": "Visit reason", "allergyUpdates": "No changes reported" }, "p_progress_note": "Nursing assessment", "p_nurse_name": "Nurse Name" }`. This authenticated RPC validates vital ranges, calculates BMI server-side, appends an auditable progress note, and atomically dispatches the token to `In Consultation`. Temperature is entered in °C and converted to the legacy Fahrenheit representation before storage. The existing `guard_visit_token_nursing_data` trigger restricts writes to nurse/admin memberships and keeps notes append-only. The existing Postgres Changes subscription propagates status and clinical updates to connected dashboards. Doctor orders, insurance statuses, diagnoses, SOAP notes, allergies, results, attachments, and encounter-linked sick leave certificates remain read-only to nursing staff.

After triage dispatch, vitals become read-only. BP at or above 140/90 is visually highlighted for nurse review; this is an alert only, not a diagnosis. Outpatient nursing treatment is available only for `Procedure` and `Service` line items at `READY_FOR_EXECUTION` with insurance status `Approved`, or with `SETTLED` billing and a cash-only/self-pay override. The nurse must first advance the token to `Ready for Treatment`; the completion RPC enforces that queue state as well as line-item eligibility. `POST /rest/v1/rpc/complete_outpatient_nurse_service` accepts `{ "p_clinic_id": "<uuid>", "p_token_id": "<token-id>", "p_line_item_id": "<line-item-id>", "p_notes": "Optional treatment note", "p_executor_name": "Nurse Name" }`; it records `treatmentExecution.executedAt` and the authenticated executor, marks the line item `COMPLETED`, and updates the token so remaining eligible treatment stays `Ready for Treatment`. Treatment records are distinct from diagnostic result payloads and are not sent to the doctor results inbox. These RPCs are defined in `supabase/migrations/202610240007_outpatient_nurse_workflow.sql`; deploy the migration before enabling the production nurse actions. The browser demo uses the same eligibility checks locally when Supabase is not configured.

Closed-loop service execution uses `line_items[].executionStatus`: doctor orders begin at `PENDING_SETTLEMENT`, an authorized cashier settlement advances eligible authorized services to `READY_FOR_EXECUTION`, and laboratory, radiology, or nursing staff can submit a result only from that state, completing the item. Encounter-linked results appear in the doctor Results Inbox and in the patient chart until acknowledged. The Supabase RPC endpoints are `POST /rest/v1/rpc/submit_visit_token_result` with `{ "p_clinic_id": "<uuid>", "p_token_id": "<token-id>", "p_line_item_id": "<line-item-id>", "p_result_payload": { "value": "14.2 g/dL", "referenceRange": "12.1–15.1 g/dL", "findings": "Result details", "status": "Normal", "reportFiles": [] } }` and `POST /rest/v1/rpc/acknowledge_visit_token_result` with `{ "p_clinic_id": "<uuid>", "p_token_id": "<token-id>", "p_line_item_id": "<line-item-id>" }`. Authenticated role memberships and database triggers enforce transitions. Result files in this browser demo are stored as data URLs; production deployments should move files to a private Supabase Storage bucket and store only authorized object paths in token results.

Doctor EMR APIs are implemented by the authenticated `doctor-api` Supabase Edge Function and its database RPCs. Deploy with `supabase functions deploy doctor-api` after applying migrations. `POST /functions/v1/doctor-api/save-emr` accepts `{ "clinicId": "<uuid>", "tokenId": "<token-id>", "doctorOrders": { "chiefComplaint": "...", "soapNotes": { "subjective": "...", "objective": "...", "assessment": "...", "plan": "..." }, "diagnoses": [], "orderedByDoctorId": "<auth-user-uuid>" }, "lineItems": [] }`; the RPC enforces assigned-doctor access, preserves existing authorization/results, appends new items at `PENDING_SETTLEMENT`, and commits the token update so the existing Realtime channel refreshes coder and cashier queues. `GET /functions/v1/doctor-api/pending-results?clinicId=<uuid>` returns completed, unacknowledged results for the authenticated requesting doctor, including encounter and patient identifiers. A gateway may expose these as `POST /api/doctor/save-emr` and `GET /api/doctor/pending-results` by rewriting to the function paths. Both endpoints require the caller's Supabase bearer token; never use a service-role key in the browser.

### CPT tariff lookup and protected pricing

Migration `202610240006_cpt_tariff_master.sql` creates the active CPT tariff master and seeds four **illustrative AED prices**. These sample prices are not payer fee schedules or DHA-approved rates: the facility must verify and replace them with its authorized tariff data before clinical or claims use. Apply the migration, then deploy the authenticated function with `supabase functions deploy cpt-api`. Staff can search using `GET /functions/v1/cpt-api/search?q=<term>`; it requires a valid Supabase bearer token and an authorized clinic membership, searches active codes/descriptions case-insensitively, and returns at most 10 tariffs. The EMR calls this endpoint after two characters. A gateway can rewrite `/api/cpt/search` to the function path.

The Patient EMR disables manual entry of CPT code, description, and unit price. Adding an item calls `POST /functions/v1/cpt-api/add` with `{ "clinicId": "<uuid>", "tokenId": "<token-id>", "cptCode": "85025", "quantity": 1, "expectedUnitPrice": 120.00 }`. The expected price is only a stale-tariff check, never the charge source: the authenticated RPC verifies the assigned doctor, re-reads the active tariff, rejects a changed price, derives unit and gross prices from the master, and appends the line item to the Visit Token (`Pending_Auth` for insured visits or `Cash_Only` for self-pay; services also begin at `PENDING_SETTLEMENT`). The browser cannot set the saved price. This API can be exposed through a gateway rewrite as `/api/cpt/add`; the client uses the Supabase function URL directly. These APIs require `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_HMS_CLINIC_ID`, an authenticated app session, clinic memberships, and the migration/function deployment.

The Medical Coder Desk surfaces pending token items and doctor appeal requests for review. Until a payer adapter is configured, staff must submit claims through the approved external channel and record only the response received from that payer. Denied items are excluded from patient charges unless a cashier records the patient's self-pay consent. After token billing, the cashier can print the receipt and download the token-based claim summary JSON.
